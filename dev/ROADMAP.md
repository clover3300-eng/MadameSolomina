## №7. Дробление portfolios.js

**Что это.** Файл `public/js/portfolios.js` — 11 тысяч строк, 888 КБ: в нём карточки,
двадцать виджетов, календарь, ребаланс-оверлей, сделки. Работает, но это один шкаф,
куда свалено всё: искать тяжело, любая правка парсит весь файл, а Клоду в сессии
приходится читать его кусками. Дробление — разложить по ящикам: несколько файлов,
у каждого своя зона. Сложность: весь файл — одно замыкание с общими переменными,
резать надо по швам (прецедент — вынос backtest.js).

**Промт:**

```
Раздели public/js/portfolios.js (~11 тыс. строк, один IIFE) на несколько файлов.

Контекст: весь файл — одно замыкание с общими переменными (store, quotes, dashCfg…),
грузится ЛЕНИВО через ensurePortfoliosJs (webapp-tabs.js) и держатель #pfLazySrc в
index.html. Прецедент выноса: backtest.js.

Требования:
- Сначала предложи план швов и согласуй со мной ДО правок: например ядро
  (store/calcPf/котировки/каркас рендера) + виджеты дашборда + вкладки/чипы/deep-link
  + ребаланс-оверлей + история сделок.
- Общее состояние — через один объект-неймспейс с явным интерфейсом, НЕ россыпь
  глобалов. ES-модули запрещены (classic scripts).
- Ленивая загрузка, preload/prefetch/hover-прогрев и версия в #pfLazySrc должны
  продолжить работать: ensurePortfoliosJs грузит части цепочкой, колбэки — только
  после ПОСЛЕДНЕЙ (держатель может стать списком файлов).
- Режь поэтапно, по одному вынесенному файлу за коммит; после каждого этапа —
  прогон dev/dev-smoke.js (24 проверки, 24/24) и клик-проверка в превью.
- Коммиты по-русски, без пуша, бампы ?v в index.html.
```

## №6. Точечные обновления DOM

**Что это.** Сейчас при каждом приходе котировок (раз в десятки секунд) вкладка
сносит ВСЮ свою разметку и строит заново — как перепечатывать весь стенд ради смены
одной цифры на табло. Вокруг этого накопились «гварды»-костыли: не сбросить курсор
в поле, не сломать перетаскивание, не закрыть попап, вернуть скроллы. Точечные
обновления — менять только изменившиеся числа, оставив полный рендер действиям
пользователя. Меньше мерцаний, меньше костылей, меньше нагрузки.

**Промт:**

```
Вкладка «Портфели» (public/js/portfolios.js): переведи ФОНОВЫЕ обновления котировок
с полной перерисовки innerHTML на точечные обновления DOM.

Сейчас softRerender/renderPortfolios на каждый тик котировок пересобирают весь
#pfWrap, из-за чего вокруг рендера живёт коллекция гвардов (фокус в полях, открытые
попапы, жесты перетаскивания, скроллы data-skey). Цель: фоновый тик обновляет только
изменившиеся ЧИСЛА (цены, суммы, проценты) через data-атрибуты на текстовых узлах;
полный рендер остаётся для действий пользователя и структурных изменений.

Требования:
- Начни с инвентаризации живых котировок по виджетам (карточки, герой, «Список
  портфелей», сводка, KPI, календарь) и размечай data-атрибутами ПОСТЕПЕННО,
  виджет за виджетом, отдельными коммитами.
- Где точечно слишком сложно (canvas-графики, спарклайны) — оставь полный рендер
  и зафиксируй комментарием; не тяни всё в один заход.
- Существующие гварды не удаляй, пока не докажешь ненужность конкретного гварда.
- Проверка после КАЖДОГО этапа: dev/dev-smoke.js (24/24) + руками в превью: при
  фоновом тике не сбрасывается курсор в поле имени и не закрывается попап
  «Видимость».
- Классические скрипты (без ES-модулей), бампы ?v, коммиты по-русски, без пуша.
```

## №9. Headless-прогон smoke-набора

**Что это.** Смоук-проверки сейчас запускаются руками: открыть сайт, вставить
содержимое dev/dev-smoke.js в консоль. «Headless»-браузер — тот же Chrome, но без
окна: запускается командой из терминала, сам открывает страницу, гоняет проверки
и печатает результат. Итог — одна команда перед коммитом вместо ручного ритуала.
Цена: первая тестовая зависимость в проекте (playwright), её надо содержать.

**Промт:**

```
Сделай запуск smoke-набора «Портфелей» одной командой, без ручного браузера.

Сейчас: dev/dev-smoke.js вставляется копипастой в консоль открытого сайта
(24 проверки, отчёт пишется в localStorage.__smoke_last, в конце набор
восстанавливает данные и ПЕРЕЗАГРУЖАЕТ страницу — учти это в ожидании отчёта).

Цель: `npm run smoke` — поднимает локальный сервер (dev/spa-server.py или
эквивалент), открывает headless-браузер, инжектит dev/dev-smoke.js, дожидается
__smoke_last, печатает таблицу результатов и выходит с ненулевым кодом при любом
FAIL.

Требования:
- Минимум зависимостей: playwright (или puppeteer) как единственная новая
  devDependency, никаких тестовых фреймворков поверх.
- Раннер положи в dev/, инструкцию — в его шапку и в шапку dev-smoke.js.
- Сам набор по возможности не меняй; если нужен машинный режим (без перезагрузки
  и тостов) — добавь флаг, не ломая ручной сценарий.
- Прогони сам и покажи вывод. Коммит по-русски, без пуша.
```

## №8. Минификация на деплой

**Что это.** Код пишется для людей: комментарии, отступы, длинные имена. Минификация —
машинная «ужимка» копии перед публикацией: комментарии и пробелы вырезаются, внутренние
имена сокращаются. Страница легче примерно вдвое, работает так же. Цена: появляется
«сборка» — ступень между «поправил файл» и «задеплоил», и отлаживать прод сложнее
(нужны sourcemaps — карты соответствия ужатого кода исходному). Проект сознательно
жил без сборки, поэтому это решение о цене, а не о технике. Делать ПОСЛЕ №7.

**Промт:**

```
Оцени минификацию JS/CSS для деплоя (сейчас public/ уезжает в Cloudflare как есть;
portfolios.js — 888 КБ сырого, 236 КБ в gzip).

Сначала — не код, а решение. Проект сознательно живёт без сборки («правлю файл —
деплою файл»). Покажи на цифрах, что даст минификация: прогони esbuild --minify по
реальным файлам проекта, таблица до/после и в gzip. Затем предложи МИНИМАЛЬНЫЙ
вариант без изменения исходников: сырцы в public/ как есть, шаг сборки только перед
деплоем (npm script, esbuild в devDependencies), выход в отдельный dist/ + правка
wrangler.jsonc на dist, sourcemaps для отладки прода.

Обязательные условия: локальные превью и правка файлов работают КАК СЕЙЧАС, без
пересборки; ?v-механика кэш-баста не ломается; деплой остаётся одной командой.
Если по цифрам или по сложности выигрыш не стоит новой ступени — скажи прямо
«не стоит» и почему.

Решение за мной: сделай замер и план, НЕ внедряй до моего «да».
```
